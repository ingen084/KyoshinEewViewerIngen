# UIテストの通信禁止の仕組み

## 隔離

1. 依存取得とビルドは通常の工程で行い、テスト対象の実行だけを別のLinuxネットワーク名前空間で行う。ループバック以外のインターフェースが存在しないことと、起動元とは異なる名前空間であることをテスト側でも検査する。VSTestのプロセス間通信には同じ隔離環境内のループバックを使う
2. 名前解決は専用mount namespace内の設定 (`hosts: files`) でローカルファイルだけに限定し、ホストの名前解決デーモンへの委譲も避ける
3. 名前空間の作成には通常は非特権user namespaceを使う。GitHubホスト等で制限される場合だけ `sudo -n unshare --net --mount` へ切り替える。どちらも利用できなければ、テストを起動せずに失敗する。ホスト全体のファイアウォールや名前解決設定は変更しない

## 監査

- テスト用HTTPは `FixtureHttpHandler` へメソッド・URL・応答を登録する。登録回数を超えた要求や未登録の要求は記録して拒否する。応答はメモリ内で生成し、DNSやソケットは使わない
- 全テストに `OfflineNetworkAttribute` を適用し、終了時に監査結果を検査する。.NETのHTTP要求とテスト用応答の使用数を照合し、直接作成したHttpClientによる未登録要求、DNS解決、IPソケット接続も検出する
- 本番の `common.props` ではEventSourceが無効なため、UIテスト側で `EventSourceSupport=true` を明示している。監査イベントの無効化や、登録したHTTP要求の診断イベントが欠落した場合も成功扱いにしない

## 失敗することの検証

通常の成功ケースの後に、以下を各1プロセスで実行する。専用の環境変数 (`KEVI_UI_TEST_NETWORK_PROBE`) で有効になる失敗検査で、対象テストが「想定外の通信要求」で失敗し、TRXと監査JSONにも違反が残ることを `verify-results.py` が確認する。単なるビルドエラーや起動失敗を成功として扱わない。試行先はlocalhostまたは応答を生成するfixtureで、外部サーバーは使わない。

- 未登録のテスト用HTTP要求を捕捉して処理する
- 直接作成したHttpClientの要求失敗を捕捉する
- DNS要求を実行する
- IPソケット接続の失敗を捕捉する

## 対象外

監査対象はテストプロセス内で動く.NETコード。自動更新のテストが起動するシェルコマンド (`chmod`・`sleep`・置き換え用のスクリプト) は同じネットワーク名前空間で動き、通信を行わない。外部プログラムを起動する本体E2Eテスト、OSネイティブのタイトルバー・通知・実GPUの検査は対象に含めない。将来.NETの子プロセスを追加する場合は、同じネットワーク隔離を継承させ、そのプロセスにも要求監査を追加する。
